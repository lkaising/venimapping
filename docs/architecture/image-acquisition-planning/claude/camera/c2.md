# Camera check c2

Camera: Allied Vision Alvium G1-130 VSWIR over PoE, firmware `14.1.D83C7207`. Device id `DEV_000A471E3D7C`. Namespace `/vimbax_camera`. Date 2026-11-23.

Labels: `[F]` is a fact from this check or with a citation. `[A]` is a working assumption. `[Q]` is an open question.

## 1. Question

Answer T6 in `coordinator/facts.md`:

1. Does the camera offer `TriggerSelector` `FrameStart`, `TriggerSource` `Software`, and the `TriggerSoftware` command?
2. With `FrameStart`, `TriggerMode` `On`, and `TriggerSource` `Software`, does one `features/command_run TriggerSoftware` give exactly one `image_raw` frame after a quiet interval of 2 s?
3. What is the time from the `command_run` call to the frame header, over five commands?

### 2.6 Deviations

1. I used `ros2 topic echo` with a timeout and without `--once`, as in check c1. A count of frames per command needs a reader that stays open.
2. I also used `ros2 service list`, `ros2 topic info`, `feature_info_query`, `get_parameters`, and `date`. These only read.
3. I called `status` six times. Each call came after the dependent write, never between a selector write and a mode or source write.
4. `ros2 topic hz` prints nothing for fewer than two messages. It served as a timed wait. The echo reader is the frame count.
5. The session could not run loops, `grep`, or inline Python. I could not synchronize the writes to the runner poll. Section 3.3 shows the effect.

## 3. Result

### 3.1 T6 part 1. The trigger features exist

1. `[F]` `TriggerSelector` offers `FrameStart`. Step 5.
2. `[F]` `TriggerSource` offers `Software`. Step 6.
3. `[F]` `TriggerSoftware` exists. It is a command feature in `/AcquisitionControl`, write only. Steps 7 and 8.
4. `[F]` `TriggerDelay` is not available on this camera at the current settings. Step 8.
5. `[F]` The original trigger state is `Off` and `Software` under all seven selectors. Step 12.

### 3.3 TriggerSoftware follows the current TriggerSelector

1. `[F]` Command 1 had no selector write before it, and it gave no frame. The selector read `ExposureActive` before and after it. Steps 10 and 25.
2. `[F]` Seven of the eight commands with a `FrameStart` write just before them gave one frame.
3. `[A]` `TriggerSoftware` acts on the selector that is current when it runs. Under `ExposureActive`, `TriggerMode` is `Off`, so the camera ignores the command. The SDK documents in `/opt/vimbax/doc` do not state this dependency.
4. `[A]` Command 6 lost the race: a runner `status` call came between its selector write and the command. I did not read the selector at that moment.
5. `[F]` A `status` call between a selector write and a mode write sent the mode write to `ExposureActive`. This happened in steps 13 and 16. It confirms facts section 1.5, item 8, on this camera.
6. `[F]` Confirmed misdirections: at least 3 of 13 windows. The runner polls `status` about every 3 s plus the guard start time. Each CLI window was about 0.5 s.
7. `[F]` `TriggerSelector` is writable during acquisition. The writes before commands 2 to 9 returned error code 0 while the stream ran. `TriggerMode` is not writable during acquisition (check c1, section 3.6).

### 3.4 Time from the command to the frame inside a process

The CLI adds start-up time before it sends a request. The driver log gives that time for `stream_start`.

| Interval | Stream 1 | Stream 2 |
|---|---|---|
| `stream_start` CLI start to `Buffer alignment` log | 283.9 ms | 273.1 ms |
| `Stream started` log to CLI exit | 188.9 ms | 200.8 ms |
| `stream_stop` CLI start to `Stream stopped` log | 389.9 ms | 389.7 ms |
| `Stream stopped` log to CLI exit | 192.3 ms | 190.9 ms |
| Total CLI time for one `command_run` | 577.9 to 589.4 ms | |

1. `[A]` The request reaches the driver about 273 to 284 ms after the CLI start. The frame then arrives about 10 to 32 ms after the driver handles `command_run`.
2. `[A]` The physical floor agrees. The exposure is 5.0 ms. 1337472 bytes at 125 MB/s take 10.7 ms. DDS adds 1.4 to 2.3 ms. The floor is about 17 ms.
3. `[A]` An in-process caller therefore gets the frame about 17 to 32 ms after it sends `command_run`.
4. `[A]` The reply leaves the CLI about 190 to 200 ms before CLI exit. The frame therefore arrives about 76 to 101 ms before the `command_run` reply.
5. `[F]` This order matches the driver. The command poll sleeps 100 ms after the first `IsDone` check, before it can reply (`driver:vimbax_camera/src/vimbax_camera.cpp:674-688`).

### 3.5 Header stamps

1. `[F]` Receipt minus header stamp is 1795400876.4585 to 1795400876.4595 s over the seven frames. The span is 1.02 ms.
2. `[F]` From command 2 to command 9, the header stamp advanced 82.2878927 s. The receipt time advanced 82.2882333 s. The difference is 0.34 ms, about 4 ppm.
3. `[F]` Check c1 measured an offset of 1795400876.4550 to .4556 s in free run, about 550 s before. The camera clock did not reset between the two checks.
4. `[Q]` The triggered offset is 3.5 to 4.5 ms larger than the c1 offset. A drift of 4 ppm explains about 2.3 ms of that. The check cannot separate drift, the stamp event under trigger, and receipt jitter.

## 5. Limits of the result

1. All numbers come from one camera, one host, and one setting: Mono8, full sensor, `ExposureTime` 4999.455 us, `AcquisitionMode` `Continuous`, `buffer_count` 7.
2. The latency has seven samples over two streams. The commands were 4 s or more apart. The check did not test a fast trigger rate, a trigger during readout, or a trigger while a frame is in transfer.
3. Each latency starts at the CLI start, which adds 273 to 284 ms. The in-process value of 17 to 32 ms is derived, not measured. Its error is about 10 ms.
4. The selector dependency of `TriggerSoftware` comes from behavior: one command without a selector write and eight with one. No document in reach states it.
5. I did not read the selector at the moment of command 6. Its cause is inferred from the runner poll.
6. The driver gap log cannot show a lost frame for commands 1 and 6. Command 1 came before the first frame of its stream, and command 6 came after the last. The absence of a `Frame with status` line is the only sign that the camera made no frame.
7. The check did not test `TriggerActivation`, other trigger sources, other selectors, or `AcquisitionMode` `SingleFrame`.
8. The quiet intervals rely on one echo reader. `ros2 topic hz` cannot report one frame.
9. The runner `status` poll ran during the whole check. It changed the selector many times during both streams. It did not change `TriggerMode` under `FrameStart`, which stayed `On` until step 33.
