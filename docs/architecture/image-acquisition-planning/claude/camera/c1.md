# Camera check c1

Camera: Allied Vision Alvium G1-130 VSWIR over PoE. Device id `DEV_000A471E3D7C`. Namespace `/vimbax_camera`. Date 2026-11-23.

Labels: `[F]` is a fact from this check or with a citation. `[A]` is a working assumption. `[Q]` is an open question.

## 1. Question

With `autostream` 0, answer T1 to T5, T7, and T8 in `coordinator/facts.md`:

1. Which `PixelFormat` values does the camera offer, and which pass the driver gate (`driver:vimbax_camera/src/vimbax_camera.cpp:1621-1651`)?
2. What are `Width`, `Height`, `WidthMax`, `HeightMax`, and `PayloadSize` at a gate-listed format?
3. What frame rate arrives on `/vimbax_camera/image_raw`?
4. Does the local device module list `DeviceTimestampFrequency`? How do header stamps relate to the host clock?
5. How long from the `stream_start` call to the first `image_raw` header?
6. While the stream is active, which of `PixelFormat`, `Width`, `AcquisitionFrameRate`, `ExposureTime`, and `TriggerMode` are writable?
7. Does `AcquisitionFrameRateEnable` exist? Read only.

If Mono12 is offered, repeat items 2, 3, and 5 at Mono12 and record the encoding. Collect driver log lines that contain `frames missing` or `Frame with status`.

## 3. Result

### 3.1 T1. Pixel formats and the gate

| Format | Offered | On the driver gate |
|---|---|---|
| Mono8 | Yes | Yes |
| Mono10 | Yes | No |
| Mono10p | Yes | No |
| Mono12 | Yes | Yes |
| Mono12p | Yes | No |
| Mono12Packed | Yes | No |

1. `[F]` The camera offers six formats. All six are available at the current settings. Steps 3 and 4.
2. `[F]` Two of the six pass the gate: Mono8 and Mono12 (`driver:vimbax_camera/src/vimbax_camera.cpp:1621-1651`). The other four leave the driver at `kStarting` if a client calls `stream_start` (`driver:vimbax_camera/src/vimbax_camera.cpp:416`, `:429-431`).
3. `[F]` The camera offers no Bayer, RGB, or YUV format. The other 18 gate entries cannot occur on this camera.
4. `[F]` The default format after driver start is Mono8. Step 4.

### 3.2 T2. Image size and payload

| Format | Width | Height | WidthMax | HeightMax | PayloadSize (bytes) | Bytes per pixel | Driver buffers at `buffer_count` 7 |
|---|---|---|---|---|---|---|---|
| Mono8 | 1296 | 1032 | 1296 | 1032 | 1337472 | 1 | 9.36 MB |
| Mono12 | 1296 | 1032 | 1296 | 1032 | 2674944 | 2 | 18.72 MB |

1. `[F]` The image is the full sensor. `Width` equals `WidthMax` and `Height` equals `HeightMax`.
2. `[F]` `PayloadSize` equals `Width` x `Height` x bytes per pixel. No chunk data adds to the payload.
3. `[F]` The published Mono8 message has `step` 1296 and 1337472 data bytes. The Mono12 message has `step` 2592 and 2674944 data bytes. Section 3.5.

### 3.3 T3. Delivered frame rate

| Format | `ros2 topic hz` rate | Window | Period min to max | `AcquisitionFrameRate` reads | Pixel data rate |
|---|---|---|---|---|---|
| Mono8 | 69.721 Hz | 1681 frames, about 24 s | 13 to 16 ms | 69.716 | 93.2 MB/s |
| Mono12 | 45.124 Hz | 415 frames, about 9 s | 21 to 23 ms | 45.110 | 120.7 MB/s |

1. `[F]` At `ExposureTime` 4999.455 us and `AcquisitionFrameRateEnable` false, the camera free-runs at the rate that `AcquisitionFrameRate` reports. That value is also the maximum of its range. Steps 9, 10, and 29.
2. `[F]` The longest interval at the `hz` reader was 16 ms at Mono8 and 23 ms at Mono12. Both are less than two frame periods. The `hz` reader therefore saw no gap of one or more frames.
3. `[F]` `DeviceLinkThroughputLimit` reads 115000000. The Mono12 pixel data rate, 120.7 MB/s, is above that number. This check does not explain the difference. `[Q]`
4. `[A]` The Mono8 rate of 69.7 Hz is a sensor or readout limit, not a link limit, because 93.2 MB/s is below the 115 MB/s value.

### 3.4 T4. Timestamp source and relation to the host clock

1. `[F]` The local device module does not list `DeviceTimestampFrequency`. The remote device module does not list it either. Steps 6 and 7.
2. `[F]` The driver therefore leaves `timestamp_frequency_` empty and publishes the raw SDK frame timestamp as nanoseconds (`driver:vimbax_camera/src/vimbax_camera.cpp:308-316`, `:1766`, `:1777`). `use_ros_time` is false. Step 15.

Header stamp and host receipt time for each sample. The offset is the host receipt time minus the header stamp.

| Sample | Format | Header stamp (s) | Host receipt (s) | Offset (s) |
|---|---|---|---|---|
| First frame | Mono8 | 12673.903003800 | 1795413550.358050696 | 1795400876.455047 |
| A | Mono8 | 12713.922763800 | 1795413590.377924421 | 1795400876.455161 |
| B | Mono8 | 12716.332555800 | 1795413592.788170043 | 1795400876.455614 |
| First frame | Mono12 | 12777.673532500 | 1795413654.139028436 | 1795400876.465496 |

3. `[F]` The header stamp is about 12,674 s, which is 3 h 31 min. The host clock is Unix time. The two clocks are not comparable without a measured offset.
4. `[F]` Over 42.43 s of Mono8 frames, the device stamp and the host receipt time advanced by the same amount within 0.57 ms. That is 13 ppm or less, including receipt jitter. The device stamp unit is therefore 1 ns, and the driver needs no frequency.
5. `[F]` The Mono8 offset varied by 0.57 ms over three samples. The Mono12 offset is 10.4 ms larger than the Mono8 offset.
6. `[A]` The 10.4 ms difference is the extra link time for the larger Mono12 payload. 1337472 more bytes at 125 MB/s take 10.7 ms. The device stamp is therefore taken before the payload transfer. It is not taken at host receipt.
7. `[F]` All four header stamps are whole multiples of 100 ns. `[A]` The camera clock resolution can be 100 ns.
8. `[Q]` The camera clock origin is about 12,674 s before the first sample. The check cannot show if that origin is power-on or the last `TimestampReset`. The check also cannot show which exposure event the stamp marks.
9. `[F]` The DDS `source_timestamp` precedes `received_timestamp` by 1.85 to 2.09 ms at Mono8 and by 4.05 ms at Mono12, on one host.

### 3.5 T5. Time from `stream_start` to the first `image_raw` header

The `/rosout` capture gives driver-side host stamps. `Buffer alignment` is logged inside `VimbaXCamera::start_streaming`, after the gate check and before the buffers are made (`driver:vimbax_camera/src/vimbax_camera.cpp:443`). `Stream started using 7 buffers` is logged after `start_streaming` returns, before the service reply (`driver:vimbax_camera/src/vimbax_camera_node.cpp:1642`).

| Interval | Mono8 | Mono12 |
|---|---|---|
| CLI start to `Buffer alignment` log | 285.5 ms | 279.6 ms |
| `Buffer alignment` log to first frame publish (`source_timestamp`) | 27.6 ms | 39.0 ms |
| `Buffer alignment` log to first frame receipt | 29.7 ms | 43.1 ms |
| `Buffer alignment` log to `Stream started` log | 108.3 ms | 111.9 ms |
| First frame receipt to `Stream started` log | 78.6 ms | 68.8 ms |
| CLI start to first frame receipt | 315.2 ms | 322.7 ms |
| CLI start to CLI exit | 589.5 ms | 701.4 ms |

1. `[F]` After the driver starts to handle `stream_start`, the first frame arrives in 30 ms at Mono8 and 43 ms at Mono12.
2. `[F]` The first frame arrives before the `stream_start` reply. The reply comes 79 ms later at Mono8 and 69 ms later at Mono12. The cause is the 100 ms sleep in the `AcquisitionStart` done poll (`driver:vimbax_camera/src/vimbax_camera.cpp:503`, `:676-688`).
3. `[F]` A reader that subscribes only after the reply misses about 5 frames at Mono8 and about 3 frames at Mono12.
4. `[F]` The 280 to 286 ms before the driver log is CLI start-up and service discovery. One CLI read call takes 586.6 ms in total. Step 16. An in-process client does not pay this cost.
5. `[F]` The `camera_info_manager` loads the calibration on the first frame. It logs `Camera calibration file /home/labuser/.ros/camera_info/DEV_000A471E3D7C.yaml not found`.

### 3.6 T7. Access modes while stopped and while streaming

| Feature | Stopped | Streaming |
|---|---|---|
| `PixelFormat` | read, write | read only |
| `Width` | read, write | read only |
| `AcquisitionFrameRate` | read only | read only |
| `ExposureTime` | read, write | read, write |
| `TriggerMode` | read, write | read only |
| `AcquisitionFrameRateEnable` | read, write | read, write |

1. `[F]` During acquisition, the camera locks `PixelFormat`, `Width`, and `TriggerMode`. It keeps `ExposureTime` and `AcquisitionFrameRateEnable` writable.
2. `[F]` `AcquisitionFrameRate` is read only also while stopped, with `AcquisitionFrameRateEnable` false.
3. `[Q]` The check did not show if `AcquisitionFrameRate` becomes writable after `AcquisitionFrameRateEnable` is true. The check also did not show if it then stays writable during a stream. The rules for this check did not allow that write.
4. `[F]` I did not read `TriggerSelector`. The `TriggerMode` result applies to the selector that was current at the time.

### 3.7 T8 and driver log lines

1. `[F]` `AcquisitionFrameRateEnable` exists on this model. It is a bool, its value is false, and it is writable in both states.
2. `[F]` The `/rosout` capture covered the full Mono8 stream and the full Mono12 stream. It has no line with `frames missing` and no line with `Frame with status`. That is about 3,100 Mono8 frames and about 630 Mono12 frames.
3. `[F]` The only warning is the missing calibration file in section 3.5.

## 5. Limits of the result

1. Each number comes from one camera, one host, and one run per format. Stamp pairs are three at Mono8 and one at Mono12.
2. All values are at one setting: full sensor, `ExposureTime` 4999.455 us, `AcquisitionFrameRateEnable` false, `TriggerMode` Off, and `buffer_count` 7. A longer exposure or a set frame rate changes T3 and the T5 frame part.
3. Only one or two readers were subscribed during each stream. The check did not load the host or the link, so it says nothing about T9 or about loss under load.
4. The T5 driver-side intervals start at the `Buffer alignment` log. That log comes after the gate check and the `PayloadSize` read. The true start of service handling is a little earlier. The check has no driver log at service entry.
5. The `rosout` stamps and the DDS receipt stamps both use the host clock. Their resolution is good, but each includes logger and executor latency of unknown size.
6. The T4 drift bound uses a 42 s span. It cannot detect drift smaller than about 13 ppm. It cannot show long-term drift or a reset of the camera clock.
7. Access modes are one read per feature at one moment. `TriggerMode` applies to the current `TriggerSelector`, which I did not read.
8. The check did not test the four formats that fail the gate. Their effect comes from the driver source only.
