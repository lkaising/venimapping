## 2. Driver contract

### Image publishing

- Fact. The `image_transport::CameraPublisher` publishes `sensor_msgs/msg/Image` and `sensor_msgs/msg/CameraInfo` as separate messages with the same header. The driver fixes the offered QoS to reliable, keep last 10, and volatile. A reliable image publisher can match reliable and best-effort subscribers with otherwise compatible QoS. Image transports depend on installed plugins and the `image_raw.enable_pub_plugins` parameter. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:350-364,1605-1633`, `jazzy:ros-perception/image_common/image_transport/src/camera_publisher.cpp:78-95,123-136`, `jazzy:ros-perception/image_common/image_transport/src/publisher.cpp:114-151`, `jazzy:ros2/rmw/rmw/include/rmw/qos_profiles.h:51-62`, `jazzy:ros2/rmw_dds_common/rmw_dds_common/src/qos.cpp:114-124`)
- Fact. The start gate accepts Mono8, Mono12, Mono16, four Bayer patterns at 8, 10, 12, and 16 bits, Rgb8, Bgr8, and three YUV422 variants. The variants are `Yuv422_8`, `YCbCr422_8`, and `YCbCr422_8_CbYCrY`. The encoding conversion covers more formats than the gate allows. The worker left-shifts admitted 10-bit Bayer and 12-bit mono or Bayer samples by 6 and 4 bits, respectively. The transform also has Mono10 and Mono14 branches, which the gate excludes. The resulting 16-bit encoding does not identify the original bit depth. (`driver:vimbax_camera/src/vimbax_camera.cpp:427-432,1621-1654,1781-1806,1835-1907`)
- Fact. The driver allocates buffers at stream start. It computes `step` from width and bits per pixel at allocation. It reads width and height from each SDK frame and sets `is_bigendian` to false. When payload size and alignment allow it, VmbC writes into the image vector. Otherwise, the frame worker copies or shifts samples from the transport buffer into the image vector. (`driver:vimbax_camera/src/vimbax_camera.cpp:420-455,1656-1715,1745-1757,1781-1806`)

### Stream start and stop

- Fact. `stream_start` and `stream_stop` use `StreamStartStop` with an empty request and an `Error` reply. Start allocates and queues buffers, starts capture, and runs `AcquisitionStart`. Stop runs `AcquisitionStop` if the camera is alive, ends capture, joins the worker, flushes the queue, and revokes buffers. The command poll adds a 100 ms sleep on the successful path of each acquisition command. (`driver:vimbax_camera_msgs/srv/StreamStartStop.srv:1-2`, `driver:vimbax_camera/src/vimbax_camera_node.cpp:1534-1595`, `driver:vimbax_camera/src/vimbax_camera.cpp:409-515,523-581,676-690`)
- Fact. The camera state machine returns success for start in `kActive` and stop in `kStopped`. It returns `VmbErrorInvalidCall` (-15) if it sees a transitional state. The node serializes start and stop with a mutex, so two competing service calls can wait for each other. The services return `VmbErrorNotFound` (-3) when the camera is unavailable. The format gate returns `VmbErrorNotSupported` (-18). Early returns can leave the state at `kStarting` or `kStopping`. A failed start or stop does not guarantee that a repeat call can recover it. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:650-654,1534-1595,1647-1662`, `driver:vimbax_camera/src/vimbax_camera.cpp:409-432,484-587`, `driver:vmbc_interface/include/VmbC/VmbCommonTypes.h:228-243`)
- Fact. The driver defaults to `autostream=1`. Its graph thread waits for a graph change or a 50 ms timeout. When the count increases and the stream is idle, it starts the stream. When the count falls to zero, it stops the stream. The automatic branches ignore the result. The count is the maximum of the image transport subscriber count and the `camera_info` count. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:292-296,579-628`, `jazzy:ros-perception/image_common/image_transport/src/camera_publisher.cpp:97-104`, `jazzy:ros-perception/image_common/image_transport/src/publisher.cpp:63-69`)
- Fact. The increase test at line 604 already holds inside that branch. An explicit stop can therefore be undone on a later count increase. A new subscriber that leaves the maximum unchanged cannot trigger that branch. With `autostream=0`, subscriber count changes do not start or stop the stream. Reconnect has a separate restart branch. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:588-618,1558-1574`)

### Single frames and triggers

- Fact. The driver provides no ROS snapshot service. The driver publishes frame pixels through the image path. Generic `features/enum_{get,set,info_get}` services expose camera trigger and acquisition enums by name. `features/command_run` can run `TriggerSoftware` if that command is available on the selected module. Its reply contains an error field and has no image or frame identifier. `features/command_is_done` reports command status separately. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:101-131,1010-1067,1071-1147,1620-1638`, `driver:vimbax_camera_msgs/srv/FeatureCommandRun.srv:1-4`)
- Fact. The driver calls the SDK command, then checks completion, sleeps 100 ms, and checks its steady-clock timeout. A successful command response therefore takes at least 100 ms. An SDK error can return before the sleep. A timeout at or below 100 ms makes a successful poll return `VmbErrorTimeout` (-12), even if the SDK had reported completion. A nonpositive parameter selects the internal 1 s poll timeout. This timeout does not include the initial SDK command call and the sleep can run past the deadline. Frames can arrive while the service call is still pending. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:1039-1065`, `driver:vimbax_camera/src/vimbax_camera.cpp:458-482,644-691`, `driver:vmbc_interface/include/VmbC/VmbCommonTypes.h:237`)
- Fact. `status` reports active or starting as streaming. It reads `AcquisitionFrameRate` and other camera features. It also writes each available `TriggerSelector` value to read its mode and source. It leaves the selector at the last successful write. A status read can interfere with a sequence that depends on the current selector. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:1468-1516`, `driver:vimbax_camera/src/vimbax_camera.cpp:1419-1473,1508-1513`)

### Timestamps, frame identity, and loss

- Fact. With the default `use_ros_time=false`, the image stamp comes from the SDK frame timestamp. The driver reads `DeviceTimestampFrequency` from the local device when available. It scales with integer division or multiplication. Without a frequency it passes the value through as nanoseconds. It does not map the camera epoch to ROS time. The code does not establish the epoch, the exposure event represented, or synchronization with any other clock. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:303-305,1605-1618`, `driver:vimbax_camera/src/vimbax_camera.cpp:308-316,1760-1778,1915-1918`, `driver:vmbc_interface/include/VmbC/VmbCTypeDefinitions.h:442-443`)
- Fact. With `use_ros_time=true`, the worker samples the driver's ROS clock after the transform and before publishing. This is a driver processing timestamp. The worker reads the parameter on each frame. Changing it during a stream can change the stamp's time basis. `camera_frame_id` is read-only and defaults to `vimbax_camera_<DeviceID>`. The driver writes it into both message headers as the coordinate frame name. (`driver:vimbax_camera/src/vimbax_camera.cpp:1745-1757`, `driver:vimbax_camera/src/vimbax_camera_node.cpp:303-321,408-418,1605-1631`, `jazzy:ros2/common_interfaces/sensor_msgs/msg/Image.msg:4-12`)
- Fact. The driver compares SDK frame IDs and logs positive gaps. The image message carries no SDK frame ID or sequence number. The SDK callback logs incomplete receive status and requeues the buffer without publishing. A normal stop clears the last frame ID. The disconnect path drops the camera object without that reset. (`driver:vimbax_camera/src/vimbax_camera.cpp:1724-1742,1910-1913`, `driver:vimbax_camera/src/vimbax_camera_node.cpp:545-555,1595-1638,1647-1662`, `jazzy:ros2/common_interfaces/sensor_msgs/msg/Image.msg:4-26`)
- Fact. Jazzy exposes an RMW `message_lost` subscription event. The local Cyclone DDS RMW reports DDS sample-lost counts and leaves both message sequence fields unsupported. Keep-last reader history can replace an unread sample without a sample-lost event. A consumer queue can count its own evictions only after receipt. These counts do not account for all missing camera frames. (`jazzy:ros2/rclcpp/rclcpp/src/rclcpp/subscription_base.cpp:162-165`, `jazzy:ros2/rmw_cyclonedds/rmw_cyclonedds_cpp/src/rmw_node.cpp:3274-3285,3943-3955`, `jazzy:eclipse-cyclonedds/cyclonedds/src/core/ddsc/src/dds_rhc_default.c:841-875`)

### Calibration

- Fact. The driver constructs `CameraInfoManager` with the device ID and read-only `camera_info_url`. The manager can load from its default file when the URL is empty. It also offers `~/set_camera_info`. If the calibration dimensions differ from the frame dimensions, the driver publishes a new `CameraInfo` with frame dimensions and zero matrices. The driver copies the image header in either case. The message definition uses `K[0] == 0` to mark uncalibrated data. Dimensional agreement alone does not check whether calibration fits the current ROI. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:408-423,1620-1631`, `jazzy:ros-perception/image_common/camera_info_manager/src/camera_info_manager.cpp:67-69,108-149,230-242`, `jazzy:ros2/common_interfaces/sensor_msgs/msg/CameraInfo.msg:20-23`)

### Events and connection

- Fact. The driver exposes camera events under `events` and feature invalidations under `feature_invalidation`. Each has `_event_subscribe` and `_event_unsubscribe` services and an `event_<name>` topic. It enables the selected device event and publishes named metadata from that event's feature category. The driver creates the topic after the subscribe request. A timer checks every 500 ms and can remove the topic before the subscription matches. A named event's availability depends on the camera. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:160-267`, `driver:vimbax_camera/src/vimbax_camera.cpp:1560-1618`, `driver:vimbax_camera_events/src/vimbax_camera_events.cpp:34-46`, `driver:vimbax_camera_events/src/event_publisher_base.cpp:43-91`, `driver:vimbax_camera_events/include/vimbax_camera_events/event_subscriber_base.hpp:117-132`)
- Fact. The driver handles VmbC discovery events internally and provides no dedicated ROS camera connection event. `connected` returns whether the driver holds a camera object. At startup, failure to open the camera shuts down the node before service initialization. After a matching `Missing` event, the driver records the streaming predicate and drops the camera. On `Detected`, a detached thread attempts to reopen it. After a successful reopen, the graph thread attempts a restart if the stream was active or starting. It makes this attempt even with `autostream=0` and clears the request without checking success. (`driver:vimbax_camera/src/vimbax_camera_node.cpp:70-131,366-382,430-465,529-568,579-618,1520-1527`, `driver:vimbax_camera/src/vimbax_camera.cpp:1508-1513`)

## 5. Design choices

### Get image

- Freshness. Is a cached recent frame sufficient, or must receipt or exposure occur after the request?
- Acquisition method. Should get image sample an active stream, start an idle stream, or request a trigger?
- Trigger association. If a trigger is required, how will get image identify its frame and handle an uncertain command result?
- Deadline. Which steps count against the request timeout, and what result should a timeout return?
- Subscription lifetime. Should an idle camera keep a matched subscription, or should each request create one?
- Feed interaction. Can get image share frames with a feed, or can it stop and restore an active feed?
- Output. Which frame layout, timestamp provenance, frame identity, and calibration fields does the caller need?

### Get image feed

- Consumer API. Should get image feed use pull, callbacks, or the ROS topic as the application contract?
- Delivery scope. Does one consumer own the feed, or does each consumer get its own queue?
- Buffer ownership. Should consumers retain the received image buffer or receive a copy?
- Buffer limit. What caps retained frames, and which frame does the feed discard at capacity?
- Transport. Which reliability and history settings meet the rate, age, and loss requirements?
- Loss reporting. Which counters and gaps should the feed expose, and how should it report missing visibility?
- Configuration. Who sets the camera format, ROI, rate, and trigger mode, and when can values change?
- Metadata. Should the feed pair camera information with images and carry device or driver time?
- Start and close. Who owns streaming, what marks readiness, and when does close stop the camera?
- Outage. Does a feed wait, close, or resume across silence, disconnect, and restart?
