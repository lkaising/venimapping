# D20 verdict on timestamp source

## Verdict

Adopt a combination. Use the Codex recommendation for phase 1 acquisition. Use Claude's device stamp measurement in the d12 feed probe.

[A] Draft against R1, R6, R9, R10, and R12. Epoch admission also assumes that the host wall clock does not step during acquisition. (`docs/architecture/image-acquisition-planning/register.md:594-605`)

1. In `camera.yaml`, set `use_ros_time: true` and `use_sim_time: false` under `/**/vimbax_camera`.
2. Set `use_sim_time: false` on the application node. Keep the time parameters fixed during acquisition.
3. In d3 and d8, use the image callback without `rclcpp::MessageInfo`. Convert `header.stamp` to the single signed 64-bit `ImageFrame::host_stamp_ns` field. Express it in nanoseconds since the Unix epoch.
4. In d11 and d22, let only the controller open epochs. Set the host wall-clock boundary under the admission lock before each controller `stream_start`. If recovery uses the driver's automatic restart, verify the profile before reopening admission. Set the boundary under the admission lock as admission reopens. Admit valid frames with stamps strictly greater than the boundary. Keep `receive_seq` increasing across epochs.
5. In d12, keep the observed counters and document the losses they cannot see. Keep `stamp_gap_frames` out of the phase 1 API. Use the steady clock for last-frame age, silence, and deadlines.
6. In d24, return the first eligible frame that fan-out delivers after the get image subscription opens.
7. For the d12 feed probe, start a separate run with `use_ros_time: false`. Measure consecutive device stamp deltas from the raw header during free run. Record DDS source stamp deltas through `rclcpp::MessageInfo` for comparison. Use the probe result to review d12 before adding a counter. Use the phase 1 settings for acquisition.

## Reasons

- [F] Both positions meet R10 on one host. With simulation time off, the ROS clock falls back to system time. On this Linux path, ROS and CycloneDDS both read `CLOCK_REALTIME`. CycloneDDS samples it immediately before `dds_write_ts` and exposes that sample as `source_timestamp`. (`ros:ros2/rclcpp/rclcpp/src/rclcpp/time_source.cpp:251-268`, `ros:ros2/rcl/rcl/src/rcl/time.c:42-48`, `ros:ros2/rcl/rcl/src/rcl/time.c:62-72`, `ros:ros2/rcutils/src/time_unix.c:58-74`, `ros:eclipse-cyclonedds/cyclonedds/src/ddsrt/src/time/posix/time.c:21-26`, `ros:ros2/rmw_cyclonedds/rmw_cyclonedds_cpp/src/rmw_node.cpp:1965-1970`, `ros:ros2/rmw_cyclonedds/rmw_cyclonedds_cpp/src/rmw_node.cpp:3280-3283`)
- [F] The driver defaults to `use_ros_time: false`, and the current YAML leaves that default in effect. With true, the frame thread transforms the image, stamps it, prepares `CameraInfo`, and calls publish. The image publishes before `camera_info`. The `CameraInfo` lookup can load calibration between the host clock reads. (`src/venimapping_bringup/config/camera.yaml:9-12`, `driver:vimbax_camera/src/vimbax_camera_node.cpp:303-305`, `driver:vimbax_camera/src/vimbax_camera_node.cpp:1605-1633`, `driver:vimbax_camera/src/vimbax_camera.cpp:1745-1757`, `ros:ros-perception/image_common/image_transport/src/camera_publisher.cpp:135-136`, `ros:ros-perception/image_common/camera_info_manager/src/camera_info_manager.cpp:129-149`)
- [A] Keep v1's host header to get the earlier d22 boundary check. If the boundary falls between the two clock reads, the header check rejects the frame and the DDS source check admits it. Both checks mark host processing events. Exposure can precede the boundary under either check because the driver queues complete frames before the transform. (`docs/architecture/image-acquisition-design-v1.md:120-129`, `driver:vimbax_camera/src/vimbax_camera.cpp:458-482`, `driver:vimbax_camera/src/vimbax_camera.cpp:1730-1757`)
- [F] In c1, the first Mono8 frame reached the matched reader 78.6 ms before the driver's success log. The service sends its reply after that log. A boundary at the reply would reject that frame. (`docs/architecture/image-acquisition-planning/claude/camera/c1.md:145-161`, `driver:vimbax_camera/src/vimbax_camera_node.cpp:1538-1554`, `driver:vimbax_camera/src/vimbax_camera_node.cpp:1641-1644`)
- [A] R1 names no required raw-topic reader outside the adapter. A host header helps such a reader if Logan adds one. The choice rests on d22 and the limited evidence for d12. (`docs/architecture/image-acquisition-planning/register.md:594-605`)
- [F] The checkpoint launch runs the driver in a separate process, and the environment script can honor an RMW override. The header keeps epoch admission independent of the RMW's source timestamp. (`src/venimapping_bringup/launch/camera.launch.py:24-41`, `scripts/env.sh:127-134`, `ros:ros2/rmw/rmw/include/rmw/types.h:633-649`)
- [F] The SDK defines the device stamp as camera-set. The driver puts it in the header with `use_ros_time: false`. It uses SDK frame IDs in its log, and the image has no frame counter. CycloneDDS can overwrite unread history without setting a loss status in that branch. (`driver:vmbc_interface/include/VmbC/VmbCTypeDefinitions.h:441-445`, `driver:vimbax_camera/src/vimbax_camera_node.cpp:1596-1618`, `ros:ros2/common_interfaces/sensor_msgs/msg/Image.msg:4-26`, `ros:eclipse-cyclonedds/cyclonedds/src/core/ddsc/src/dds_rhc_default.c:854-875`)
- [A] Both host stamp deltas can count time spent in the driver queue as missing camera periods. A publish delay can hold the current SDK buffer while complete frames queue. At a 14.34 ms period, the proposed formula counts five missing frames for an 80 ms host stamp gap. That count can occur even if every frame arrives. The device stamp gives the probe a way to test that error independently of host delay. (`driver:vimbax_camera/src/vimbax_camera.cpp:458-482`, `driver:vimbax_camera/src/vimbax_camera_node.cpp:1631-1638`, `ros:eclipse-cyclonedds/cyclonedds/src/core/ddsi/src/q_transmit.c:1248-1269`, `docs/architecture/image-acquisition-planning/claude/positions.md:270-275`)
- [Q] Do device stamp deltas meet the d12 half-period limit without loss, and do they estimate known gaps under load? Use the 30 Hz profile and 69.7 Hz design load. Use known omissions to test reader-side gaps. Driver gap logs can help check SDK gaps. The stamp origin, exposure event, and reset behavior across an outage remain open. (`docs/architecture/image-acquisition-planning/register.md:255-263`, `docs/architecture/image-acquisition-planning/codex/camera/c3.md:45-65`, `docs/architecture/image-acquisition-planning/claude/camera/c1.md:137-143`, `docs/architecture/image-acquisition-planning/claude/camera/c2.md:150-155`)
